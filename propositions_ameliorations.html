Propositions d'améliorations
Application de gestion scolaire

Ce document présente les recommandations formulées à l'issue de l'analyse complète de l'application de gestion scolaire (backend Laravel 11, frontend React 18, application mobile Flutter). Les améliorations sont classées par priorité et par domaine d'impact.

🔴 Priorité haute — Sécurité & Intégrité

1. Sécurisation des mots de passe parents

Le mot de passe par défaut « 12345 » est un placeholder fonctionnel mais insuffisant pour une mise en production. Toute personne connaissant un numéro de téléphone d'un parent peut accéder aux données de ses enfants.

Actions recommandées :

  • Générer un mot de passe aléatoire sécurisé à la création de chaque compte parent.
  • Transmettre ce mot de passe par SMS au numéro enregistré.
  • Ajouter un écran « Changer mon mot de passe » dans l'application mobile.
  • Imposer un changement de mot de passe à la première connexion.

2. Activation de l'authentification web (interface d'administration)

L'interface web React est actuellement accessible sans aucune connexion. Le code d'authentification existe côté backend (AuthController, routes commentées) mais n'est pas activé. N'importe qui accédant à l'URL peut consulter et modifier toutes les données scolaires.

Actions recommandées :

  • Décommenter les routes d'authentification dans api.php.
  • Activer le composant Login.jsx et PrivateRoute.jsx déjà présents dans le frontend.
  • Définir des rôles : Administrateur, Enseignant, Secrétariat.

3. Validation des chevauchements dans l'emploi du temps

Le système accepte actuellement la création de deux créneaux au même horaire pour la même classe, ou le même enseignant affecté à deux classes simultanément.

Actions recommandées :

  • Ajouter une règle de validation côté backend : vérifier les chevauchements avant insertion.
  • Afficher un message d'erreur explicite dans le formulaire React.

🟠 Priorité moyenne — Fonctionnalités

4. Export des bulletins en PDF

Les parents visualisent les notes sur l'application mobile mais ne peuvent ni les imprimer ni les archiver. Un export PDF officiel avec entête de l'établissement est attendu par les familles.

Actions recommandées :

  • Intégrer la librairie barryvdh/laravel-dompdf côté backend.
  • Créer un endpoint GET /parent/enfant/{id}/bulletin/{periodeId}/pdf.
  • Ajouter un bouton « Télécharger le bulletin » dans l'application mobile.

5. Notifications push pour les parents

Aucun système d'alerte n'informe les parents en temps réel des absences de leurs enfants, des nouveaux devoirs ou des informations de l'établissement.

Actions recommandées :

  • Intégrer Firebase Cloud Messaging (FCM) côté backend et Flutter.
  • Déclencher une notification lors de la saisie d'une absence.
  • Notifier à la publication d'une nouvelle information établissement.

6. Gestion des paiements de scolarité

La table scolarites définit les échéances de paiement mais ne trace pas les paiements effectués. Il est impossible de savoir quelles familles sont à jour.

Actions recommandées :

  • Créer une table paiements (montant, date, mode, parent_id, echéance_id).
  • Ajouter une interface de saisie des paiements dans le frontend.
  • Afficher le statut payé/impayé dans l'application mobile parent.
  • Générer des relances ou reçus PDF.

7. Tableau de bord statistiques (page d'accueil)

La page d'accueil de l'interface web est actuellement vide. Un tableau de bord donnerait une vision globale de l'établissement en un coup d'œil.

Indicateurs suggérés :

  • Nombre total d'élèves, enseignants, classes.
  • Taux d'absence global et par classe.
  • Moyennes générales par niveau.
  • Prochains devoirs planifiés.
  • Dernières informations publiées.

🟡 Qualité technique

8. Pagination des listes

Plusieurs endpoints retournent l'intégralité des données (::all()) sans pagination. Avec une croissance des données, cela entraînera des temps de chargement élevés et une surcharge mémoire.

Actions recommandées :

  • Remplacer ::all() par ::paginate(25) sur les listes principales.
  • Adapter les composants React pour gérer la navigation entre pages.

9. Tests automatisés

Aucun test automatisé n'est en place. Toute modification du code présente un risque de régression non détectée.

Actions recommandées :

  • Tests PHPUnit backend : authentification, calculs de moyennes, règles métier.
  • Tests d'intégration sur les routes API critiques (bulletin, assiduités).
  • Tests React sur les formulaires principaux (création élève, saisie notes).

10. Gestion de l'expiration du token (application mobile)

Lorsque le token Sanctum expire, l'application mobile reçoit une erreur 401 mais ne redirige pas automatiquement vers l'écran de connexion. L'utilisateur reste bloqué sur un écran d'erreur.

Actions recommandées :

  • Ajouter un intercepteur Dio qui détecte les réponses 401.
  • Effacer le token stocké et rediriger vers l'écran de connexion.
  • Configurer une durée de vie raisonnable pour les tokens Sanctum.

🟢 Expérience utilisateur

11. Photo de profil de l'élève

L'application affiche un avatar généré avec l'initiale du nom. Une vraie photo facilite l'identification des élèves, particulièrement utile pour les enseignants.

Actions recommandées :

  • Ajouter un champ photo sur la table eleves.
  • Gérer l'upload côté Laravel (Storage::disk('public')).
  • Afficher la photo dans l'application mobile et le frontend.

12. Messagerie parent-établissement

Les parents n'ont aucun moyen de contacter l'établissement via l'application. Un système de messages simples réduirait les appels téléphoniques et centraliserait les échanges.

Actions recommandées :

  • Créer une table messages (expéditeur, destinataire, contenu, date, lu).
  • Ajouter un écran « Messages » dans l'application mobile.
  • Ajouter une interface de réponse dans le frontend d'administration.

13. Calendrier scolaire

Les dates importantes (vacances, examens de passage, réunions parents-professeurs) ne sont pas visibles dans l'application mobile. Les parents consultent d'autres sources.

Actions recommandées :

  • Créer une table evenements (titre, date_debut, date_fin, type).
  • Intégrer un vue calendrier dans l'application mobile Flutter.
  • Permettre à l'administration d'ajouter des événements depuis le frontend.
